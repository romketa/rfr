## rfr-api

- `./gradlew build` does not validate HQL in `@Query`: query errors surface only at application startup against a live DB.
- Types in `io.student.rangiffler.model.types` are generated by DGS Codegen; never write them by hand. `UserConnection`/`PhotoConnection`
  are not declared in the schema (IDEA shows them red, that is expected): Spring GraphQL synthesizes them, `typeMapping` maps them to `Page<...>`.
- Controller arguments are `@Argument("name") @Nullable Integer`: a client may send an explicit `null` that breaks `int`, and builds
  without `-parameters` (e.g. VS Code) fail on unnamed arguments.
- Never call `@SchemaMapping` methods directly; Spring calls them when the client asks for the field.
- Security is method-level: `POST /graphql` passes the filter chain, controllers carry class-level `@PreAuthorize`
  (queries `read`, mutations `write`). New controllers follow the same split.
- Friendship conflicts surface on flush: keep `saveAndFlush`/explicit `flush()` inside the `try`, otherwise the exception fires at commit,
  outside the service method, and becomes `INTERNAL_ERROR`.
- Spring Boot 4 uses Jackson 3: `tools.jackson.databind.*`, not `com.fasterxml.jackson.databind.*`.

## Real vs mocked

- Real (persisted): `Query.user`, `Query.users`, `User.friends`/`incomeInvitations`/`outcomeInvitations`, `Mutation.user`,
  `Mutation.friendship`, `Query.countries`.
- Mocked (`*Mock*` classes + `resources/mock/*.json`, nothing persisted): `Query.feed`, `Feed.photos`, `Feed.stat`, `Photo.likes`,
  `Mutation.photo` (returns the built photo; a like is lost because the JSON is re-read on every call), `Mutation.deletePhoto` (always `true`).
- **Never replace the mocks with a real implementation on your own.** Do not make the mocks persist data and do not start using the
  `photo`/`like`/`photo_like`/`statistic` tables unless the user explicitly asks. If a task (e.g. a failing e2e test on photos or likes)
  seems to need real data, stop and ask.
