# What is reviewed
A resource is everything a test receives and must give back: rows in rangiffler-auth and rangiffler-api, `Page`, `BrowserContext`.
For every resource find the owner, where it is acquired, where it is kept and where it is released; a resource with no answer to one of these is the finding.

# Rules
1. **Owner is the decorator tree.** The `ExtensionContext.Store` holds only the root `UserFixture` from `UserRequest.fixture()` and closes it as `AutoCloseable`; each `UserWithRelationsFixture` (one per `Relation`: `FRIEND`, `INCOME_INVITATION`, `OUTCOME_INVITATION`) owns its `origin` and the `related` users it created. Extension fields, statics and `ThreadLocal`s never own a resource.
2. **Register before partial setup.** `UserExtension.beforeEach` calls `store.put(parameter, fixture)` before `fixture.create()`; `create()` is not atomic (`AuthAccount`, `Profile`, related users, `Friendship`), so `close()` must work after a failure at any step and be a no-op before `create()`.
3. **create and close are symmetric.** A decorator deletes exactly what it created, addressed by username or id, in reverse order (its friendship rows, related users, `delegate`) through `TearDown`, so every step runs and the first failure is thrown with the rest suppressed. Broad `DELETE` or `TRUNCATE` is a defect.
4. **New relation is a new `Relation` value, new kind of precondition is a new decorator.** Compose a decorator in `UserRequest.fixture()`; a flag in `SingleUserFixture`, a branch in `UserExtension` or a fourth copy of `UserWithRelationsFixture` is a defect. The extension knows only `UserRequest` and `UserFixture`.
5. **One @User is one parameter.** Each `@User TestUser` parameter is one fixture under its own `Parameter` key in the Store; related users live inside `TestUser` (`friends`, `incomeInvitations`, `outcomeInvitations`) and the fixture tree, never as extra parameters.
6. **Browser resources belong to BrowserExtension.** `@WebTest` registers it; `Page`, `BrowserContext` and `Playwright` are created and closed there only, never in tests, page objects or other extensions.
7. **Layers.** `jupiter` has no SQL and no locators; `data` has no JUnit API and no `Jdbc` calls outside `data/db`; `data/db` does not depend on `data`; `test` has no locators and no SQL.
8. **Class-level extensions are declared on the class or a static field.** An extension that implements `BeforeAllCallback` or `AfterAllCallback` may be registered declaratively only with `@ExtendWith` on the test class (directly, through a composed annotation such as `@WebTest`, or inherited from a superclass or interface) or on a `static` field. `@ExtendWith` with such an extension on a method, on an instance field, on a constructor parameter or on a parameter of a test or lifecycle method is a defect, even when the run looks green: a method-level registration never gets `beforeAll`/`afterAll`, and the other places hide a class-level registration behind a member declaration. Evidence: the trace of `test/fake/ExtendWithPlacementsTest` with `DemoExtension` (`-i`), which shows which scenarios get `beforeAll`/`afterAll`.
9. **An extension is safe for any test in the project.** It must not assume where it was registered: the same class may be declared over one test method, over a class (directly or through a composed annotation such as `@WebTest`) or globally through `ServiceLoader` autodetection, and then it runs for tests that have no `@User`, no `TestUser` parameter or a different signature altogether. So before creating test data it inspects the test method it actually runs for: it takes the method from `context.getTestMethod()`, filters its parameters by annotation, type and declaring executable with the same check that `supportsParameter` uses (`UserExtension.isUserParameter`), creates data only for the parameters that pass, and does nothing when none passes. A `beforeEach` that creates a user unconditionally, reads a parameter by position, resolves a parameter it did not create, calls `getRequiredTestMethod()` where a class-level context is possible (`beforeAll`, `preConstructTestInstance`, `resolveParameter` for a constructor or lifecycle-method parameter) or throws for a test that merely lacks its annotation is a defect. Evidence: the extension registered over `ExtendWithPlacementsTest.OnClass` or over a class with a `@Test` without parameters must leave the run green and the database unchanged.
10. **Declarative registration by default.** An extension is registered with `@ExtendWith`, directly or through a composed annotation such as `@WebTest`; it reads its settings from `Config`, annotations and the `ExtensionContext`, so it has a no-argument constructor and JUnit instantiates it. Programmatic registration with `@RegisterExtension` is allowed only when the extension has to be configured through a constructor or a builder, and the field then shows that configuration. A `@RegisterExtension` field holding a `new XExtension()` with no arguments, or a `static` field used only to control order, is a defect: it duplicates what `@ExtendWith` does and bypasses the registry's deduplication by type (rule 8).
11. **`SuiteExtension` implementations are registered only globally through `ServiceLoader`.** `beforeSuite` runs on the first `beforeAll` that reaches the extension and `afterSuite` when the root `Store` closes; that is "once per run, before every test and after the last" only when every class carries the extension, which only `META-INF/services/org.junit.jupiter.api.extension.Extension` with `junit.jupiter.extensions.autodetection.enabled=true` guarantees. `@ExtendWith(XSuiteExtension.class)` on a class, a composed annotation, a field or `@RegisterExtension` is a defect even when the run looks green: classes without it run before `beforeSuite` or, in a parallel run, concurrently with it. The services file lists only concrete implementations with a public no-arg constructor, never the `SuiteExtension` interface (ServiceLoader fails at engine start and no test runs). The only exception is a `@ProbeTarget` in `jupiter/probe/SuiteExtensionTest`, because the probe selects exactly those classes.
12. **Every conclusion is backed.** A finding cites a probe in `jupiter/probe/UserExtensionTest` (EngineTestKit, `find()`/`exists()` from `data/db`, entries published through `TestReporter`, the failing and the unknown-country scenarios) or a concrete file and line. Without a found cause, propose no change.

# Answer format
- For every resource: owner, acquisition, storage, release.
- For every finding: file and line, the failure scenario, how to reproduce it (which probe, or which `create()` step has to fail).
- Three lists: confirmed by a run, by reading the code, not checked.
- No defects: say so and list the limits of the current design.
